## شرط المالك الإضافي — فحص شامل قبل الانتقال (ملزم لجميع المراحل)

لا يجوز إغلاق أي مرحلة أو الانتقال إلى التالية إلا بعد تنفيذ مراجعة عميقة ومعالجة جميع العيوب والثغرات والفجوات المكتشفة، ثم إعادة الفحص على SHA نهائي ثابت. يجب تشغيل كل فحص واختبار متاح في GitHub وملائم لنطاق المرحلة، وليس الاكتفاء بـ workflow واحد. تشمل مصفوفة الفحص الإلزامية:

1. **مراجعة التغيير:** diff كامل، مراجعة الملفات المتأثرة، الاعتماديات، التعارضات، API/schema/data migrations، التوافق العكسي، وتتبع المتطلبات إلى الاختبارات.
2. **التحليل والبناء:** format/lint/static analysis، type checking، compile/build لكل منصة مدعومة وممكنة، والتحقق من lockfiles وworkflow YAML.
3. **اختبارات البرمجيات:** unit، component/widget، integration، emulator، contract/API، end-to-end، regression، negative/authorization، concurrency/race، idempotency/replay، migration/backup/restore، وproperty/fuzz tests حيث توجد أدوات مناسبة.
4. **الأمن:** CodeQL/code scanning إن أمكن تفعيله، dependency/SCA and vulnerability audit، secret scanning، dependency review، قواعد Firestore/Storage، authorization/privilege escalation، input validation، upload/scanner، SSRF/XSS/CSRF عند انطباقها، وسجلات التدقيق.
5. **الجودة والتشغيل:** الأداء والحمل والضغط، حدود الموارد والتكلفة، resilience/retry/timeouts، observability/logging، accessibility، localization/RTL، وتجربة الأجهزة والمنصات حيث تتوفر بيئة اختبار.
6. **التحقق من GitHub نفسه:** جميع workflows ذات الصلة، required checks المتاحة، artifacts وتقاريرها، نتائج PR review threads، وفحوصات الفرع والحماية التي تسمح بها صلاحيات الاتصال.
7. **إدارة الثغرات:** كل finding يصنف severity وموضعه وأثره؛ P0/P1 يمنع الإغلاق، ويجب إصلاح findings ضمن النطاق ثم إعادة الاختبار. لا تقبل استثناءات إلا بقرار مالك موثق مع سبب وضوابط تعويضية، ولا يجوز تجاوز عيوب أمنية حرجة.

**قواعد الصدق والتغطية:** لا يوجد اختبار واحد يثبت «كل شيء». لا تُشغّل اختبارات غير ذات صلة لمجرد العدد؛ يجب توثيق سبب عدم الانطباق أو عدم توفر الأداة/الصلاحية/البيئة، واعتبارها فجوة قبول إذا كانت لازمة. GitHub لا يوفر وحده كل اختبارات الأجهزة الحقيقية أو المراجعة القانونية؛ تلك بوابات منفصلة. لا يُعلن اكتمال فحص غير منفذ.

## قواعد إدارة التنفيذ

1. ننفذ المراحل بالترتيب أدناه؛ لا ننتقل إلى المرحلة التالية قبل إغلاق الحالية.
2. لكل مرحلة: نطاق محدد، تغييرات صغيرة، اختبارات على SHA ثابت، مراجعة أمنية/دلالية، ثم سجل إغلاق.
3. الإغلاق يعني: جميع مخرجات المرحلة موجودة، اختبارات القبول ناجحة، لا عيوب P0/P1 مفتوحة ضمن نطاقها، والملفات/القرارات/الاختبارات موثقة.
4. عند الفشل: تبقى المرحلة مفتوحة، ويُسجل السبب والإصلاح وإعادة الاختبار؛ لا نتجاوز الفشل.
5. لا دمج شامل للفروع؛ ننتقي التغييرات بعد مقارنة الملفات والاعتماديات، ونحتفظ بتاريخ الفروع حتى اكتمال المصالحة.
6. لا دمج إلى `main`، ولا نشر، ولا تعديل Firebase حي، ولا تفعيل Billing/Blaze أو خدمات مدفوعة، ولا تحصيل أموال حقيقية ضمن هذه الخطة دون موافقة منفصلة صريحة.
7. مختبر 5,000 شخصية يبقى في مستودعه المستقل ويختبر SHA مثبتاً من المنصة.
8. أي بند قانوني يحتاج مستند شركة رسمي أو مراجعة محامٍ يبقى «محجوباً» ولا يُعلن مطابقاً أو نافذاً.

## نموذج إغلاق كل مرحلة

عند اكتمال أي مرحلة، يضاف سجل يتضمن:
- رقم المرحلة واسمها.
- الملفات والـ commits التي تغيرت.
- SHA النهائي الدقيق.
- أسماء workflows وأرقام التشغيل ونتائجها.
- نتائج اختبارات القبول اليدوية/الأجهزة عند انطباقها.
- العيوب المفتوحة والمخاطر المتبقية.
- رابط الأدلة والقرار: **مغلقة** أو **تبقى مفتوحة**.
- اسم/صفة صاحب الموافقة عندما تتطلب المرحلة قبول المالك.

**الحالة الحالية:** المرحلة 0 موثقة جزئياً، والمرحلة 1 لم تُغلق. نقطة التنفيذ التالية هي إغلاق جرد الفروع/PRs/الملفات والـ commits ومصالحتها، مع استكمال التحقق الدقيق من PR35 وPR38. لا يبدأ تنفيذ مالي جديد قبل تثبيت خط الأساس ومراجعة التغييرات المتداخلة.
