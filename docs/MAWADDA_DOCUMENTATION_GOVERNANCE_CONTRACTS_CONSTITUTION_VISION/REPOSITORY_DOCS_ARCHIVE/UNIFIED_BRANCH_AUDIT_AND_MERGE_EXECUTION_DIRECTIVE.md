# توجيه المالك التنفيذي: التدقيق الشامل وتوحيد جميع الأعمال في فرع التطوير

**المعرّف:** GOV-MAWDDA-UNIFIED-001  
**التاريخ:** 2026-11-21  
**الحالة:** توجيه تنفيذي موثق بناءً على طلب المالك  
**المستودع:** `productionhome2022-hash/mawda-platform`  
**الفرع المستهدف الوحيد:** `codex/mawda-full-platform-implementation`

## 1. الغرض والنطاق

هذا التوجيه ملزم لمسار تدقيق وتوحيد الأعمال والفروع وطلبات الدمج الخاصة بمنصة Mawdda. الهدف هو تكوين مصدر تطوير موحد متكامل، بعد فحص التغييرات الفعلية ومحتويات الملفات واعتماد سلامتها وتوافقها، وليس مجرد مقارنة أسماء الفروع أو رؤوس commits.

يشمل النطاق جميع الفروع ذات الصلة، وطلبات السحب المفتوحة والمغلقة ذات التغييرات غير المستوعبة، والملفات والأكواد والوثائق والاختبارات والإعدادات والقواعد والمخططات وسير العمل والتبعيات المرتبطة بها.

## 2. أمر المالك: أولوية التوحيد قبل الاختبارات

1. الأولوية الحالية هي التدقيق والنقل والدمج إلى فرع التطوير الموحد.
2. **تُعلّق خلال مرحلة النقل والدمج جميع عمليات الاختبار الخارجية ومحاكاة 5000 شخصية، ولا تُشغّل اختبارات 5000 شخصية كشرط سابق للتوحيد.**
3. لا تُنشأ تشغيلات CI أو workflows أو مطالبات تحقق خارجية جديدة أثناء أعمال التوحيد إذا كانت تشغّل اختبارات أو محاكاة خارجية؛ وتُراجع إعدادات التشغيل بما يمنع بدء هذه الاختبارات خلال هذه المرحلة.
4. لا يُجرى اختبار 5000 شخصية ولا اختبار تكامل خارجي شامل إلا بعد اكتمال توحيد الفروع والملفات واستقرار الفرع الموحد، وبقرار مرحلة لاحقة.
5. هذا التوجيه يوثق ترتيب العمل ولا يثبت بذاته إيقاف تشغيل قائم أو إلغاءه. أي إلغاء فعلي لتشغيل قائم يجب أن يسجل كإجراء مستقل مع رقم التشغيل ونتيجته، ولا يُدّعى حصوله دون دليل.
6. لا تؤخر اختبارات 5000 شخصية نقل التغييرات السليمة إلى الفرع الموحد؛ موضعها بعد التوحيد.

## 3. منهج التدقيق الإلزامي

لا يُعد التدقيق مكتملاً بمقارنة رؤوس الفروع أو قوائم الملفات فقط. لكل فرع وPR ذي صلة يجب:

1. حصر جميع الفروع وPRs، وتسجيل الحالة، والقاعدة والفرع المصدر، وSHA الطرفين، وحالة Draft، وإمكانية الدمج، والملفات المتغيرة، والـcommits.
2. فحص تاريخ commits والعلاقات بينها وتحديد التغييرات المشتركة والمكررة والموجودة مسبقاً في الفرع الموحد، لمنع التكرار أو فقدان التغييرات.
3. إعداد قائمة كاملة بالملفات المتغيرة لكل مصدر، بما في ذلك الملفات المحذوفة والمعاد تسميتها والملفات الثنائية والملفات المولدة والإعدادات المخفية وملفات CI.
4. قراءة المحتوى الكامل لكل ملف مرشح للنقل في مصدره، وقراءة النسخة المقابلة في الفرع الموحد، وعدم الاكتفاء بالمقتطفات أو أسماء الملفات أو ملخصات PR.
5. تدقيق التغييرات على مستوى الأسطر والرموز والأوامر والتهيئة والعقود البرمجية، مع التحقق من أثرها وسياقها قبل وبعد التغيير. لا يُقبل ادعاء فحص «كل حرف» ما لم تكن هناك أدلة آلية ومراجعة موثقة تغطي المحتوى الفعلي.
6. تتبع الاعتماديات والاستخدامات المتقاطعة، بما يشمل imports، callers، exports، نماذج البيانات، مخططات Firestore، قواعد Firestore وStorage، Cloud Functions، واجهات Flutter، الخدمات، الفهارس، إعدادات المنصات، الأسرار المشار إليها دون كشفها، workflows، الاختبارات، والوثائق.
7. فحص التوافق بين كل مجموعة تغييرات وبين النظام المتكامل، وليس كل PR بمعزل عن بقية الفروع. يجب كشف التعارضات الوظيفية والمعمارية وتعارضات أسماء الحقول والمسارات والصلاحيات وسياسات الاحتفاظ والاقتصاد.
8. عدم إسقاط ملف أو commit أو جزء من تغيير بصمت. كل ملف أو تغيير يجب أن تكون له نتيجة موثقة: نُقل، موجود مسبقاً، مكرر، غير ذي صلة، مستبعد لسبب موثق، أو محجوب بقرار/خطر يحتاج المالك.
9. الحفاظ على أقل تغيير آمن، وعدم تخفيف التحقق أو تعطيل الحماية أو الاختبارات لتجاوز مشكلة دمج.
10. لا يُدمج Draft أو تغيير غير مكتمل أو تغيير يمس قراراً سيادياً لمجرد وجوده في PR مفتوح؛ يُفحص ويصنف، ويُحجب عند الحاجة إلى قرار المالك.

## 4. قواعد النقل والدمج

- الفرع المستهدف هو حصراً `codex/mawda-full-platform-implementation`.
- تُنقل إليه التغييرات المطلوبة والمعتمدة بعد اكتمال تدقيقها وتبعياتها وحل التعارضات.
- يجب أن يكون النقل منظماً وقابلاً للتتبع، مع الحفاظ على تاريخ التغيير حيث أمكن وتجنب cherry-pick أو الدمج الآلي السطحي الذي يكرر أو يطمس التغييرات.
- لا يُسمح بالدمج إلى `main)، ولا النشر، ولا تعديل الإنتاج أو Firebase الإنتاجي، ولا تفعيل الفوترة أو الموارد المدفوعة، ولا حذف بيانات أو موارد، ولا تغيير سياسات الاحتفاظ الحية.
- لا تُغلق PRs ولا تُحذف الفروع المصدرية أثناء عملية التوحيد لمجرد نقل محتواها؛ تبقى مصادر التغيير محفوظة إلى أن يُوثق مصيرها ويُتخذ قرار مستقل بشأن التنظيف.
- عند وجود تعارض لا يمكن حسمه من قرارات المشروع أو الوثائق الأصلية، يتوقف الجزء المتأثر ويُرفع للمالك بدلاً من التخمين.
- لا يجوز استبدال إعدادات iOS الصحيحة أو تغيير هوية التطبيق `com.mawdda.platform.app` أو مشروع Firebase المعتمد `mawda-app-2026` دون موافقة مستقلة.
- لا تُدخل أسراراً أو مفاتيح أو ملفات اعتماد إلى المستودع.

## 5. معالجة العيوب والفجوات

يجب تسجيل كل خطأ أو ثغرة أو فجوة أو تعارض مكتشف، وتصنيف شدته ونطاق أثره وسبب جذره، ثم إصلاحه ضمن صلاحيات التطوير عندما يكون الحل واضحاً وآمناً ولا يغير قراراً سيادياً.

لا يجوز إخفاء مشكلة عبر حذف اختبار أو خفض assertion أو توسيع صلاحيات أو تعطيل قاعدة أمان. يجب أن يتضمن كل إصلاح اختباراً مناسباً أو تفسيراً موثقاً لتعذر الاختبار في مرحلة التوحيد.

إذا احتاج الإصلاح إلى تغيير سياسة أو سعر أو حصة أو مدة احتفاظ أو صلاحية مالك أو مورد إنتاجي أو قرار تجاري، فيُحجب ذلك الجزء لحين موافقة المالك.

## 6. التوثيق وسجل التتبع

يجب أن يحتوي سجل التوحيد النهائي على الأقل على:

- تاريخ التدقيق وSHA الأساس للفرع الموحد وSHA النهائي بعد النقل.
- قائمة جميع الفروع وPRs التي جرى فحصها.
- لكل PR/فرع: base/head SHA، حالة Draft، الملفات، commits، والقرار النهائي.
- لكل تغيير: الملفات التي نُقلت أو كانت موجودة مسبقاً أو استُبعدت أو حُجبت، مع السبب.
- التعارضات المكتشفة وطريقة حلها أو سبب إبقائها محجوبة.
- العيوب والثغرات والفجوات التي عولجت، وما بقي منها.
- الاختبارات التي شُغلت فعلاً خلال هذه المرحلة، مع SHA ونتائجها؛ ويجب أن يذكر صراحةً أن الاختبارات الخارجية ومحاكاة 5000 شخصية معلقة حتى ما بعد التوحيد.
- روابط commits وPRs وملفات الأدلة ونتائج CI ذات الصلة.
- قائمة تحقق نهائية تثبت أن جميع مصادر التغيير ذات الصلة قد تمت محاسبتها ولم يُترك تغيير بلا تصنيف.

## 7. سياسة التواصل والتقارير

- لا ترسل تقارير لحظية أو مرحلية أو تقارير تقدم أثناء التدقيق والنقل والدمج.
- لا تطلب من المالك نسخ سجلات أو مخرجات أدوات إذا كان بالإمكان استخراجها مباشرة من GitHub أو الأدوات المتاحة.
- لا تطلب من المالك إعادة شرح هذا التوجيه أو تكراره في المحادثات اللاحقة؛ يجب الرجوع إلى هذه الوثيقة.
- يُقدّم تقرير واحد نهائي بعد اكتمال النطاق، يوضح النتائج الفعلية والأدلة والملفات وSHA والاختبارات والمتبقي.
- الاستثناء الوحيد للتواصل قبل التقرير النهائي: عائق جوهري يتطلب صلاحية أو قراراً سيادياً من المالك. عندها يُطرح سؤال محدد واحد يوضح الإجراء المحجوب وسبب الحاجة إلى القرار.
- لا يُدّعى اكتمال التدقيق أو التوحيد أو إصلاح جميع العيوب دون أدلة قابلة للتحقق.
- لا يمكن ضمان انعدام جميع الأخطاء أو الثغرات بصورة مطلقة؛ يجب وصف التغطية وحدود الفحص والنتائج بدقة.

## 8. بوابة إغلاق مرحلة التوحيد

لا تعتبر مرحلة التوحيد مكتملة إلا بعد تحقق جميع ما يلي:

- [ ] حصر جميع الفروع وPRs ذات الصلة.
- [ ] فحص commits والعلاقات والتغييرات المتكررة.
- [ ] قراءة ومقارنة كل ملف ذي تغيير فعلي مرشح للنقل، مع تتبع تبعياته.
- [ ] تصنيف كل تغيير دون إسقاط صامت.
- [ ] نقل جميع التغييرات السليمة والمعتمدة إلى فرع التطوير الموحد.
- [ ] حل التعارضات أو توثيق حجبها وسببها.
- [ ] معالجة الأخطاء والفجوات التي تقع ضمن التفويض.
- [ ] توثيق SHA النهائي ومصفوفة الملفات ومصير كل PR/فرع.
- [ ] التحقق من أن `main` والإنتاج وFirebase الإنتاجي والفوترة وسياسات الاحتفاظ الحية لم تتغير.
- [ ] عدم تشغيل محاكاة 5000 شخصية أو الاختبارات الخارجية كجزء من مرحلة النقل والدمج.
- [ ] إعداد التقرير النهائي بالأدلة والقيود والمهام المتبقية.

بعد اجتياز بوابة التوحيد فقط، تُحدد مرحلة تحقق تكاملي لاحقة تشمل الاختبارات المناسبة ومحاكاة 5000 شخصية، وفق صلاحيات المشروع وقرارات المالك.
