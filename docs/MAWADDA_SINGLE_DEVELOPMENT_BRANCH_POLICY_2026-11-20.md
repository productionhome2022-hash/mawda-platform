## 1. القرار الإداري الحاسم

يعتمد المشروع **فرع تطوير متكامل موحد واحد فقط**. الفرع الوحيد المعتمد مرجعاً للتطوير والدمج الداخلي والنقل والبناء والاختبارات هو:

`codex/mawda-full-platform-implementation`

يُمنع إنشاء أو اعتماد فروع تطوير موازية للميزات أو المراحل أو الإصلاحات أو الاختبارات أو التخصصات. لا تنشأ فروع جديدة لمجرد تقسيم العمل أو تسهيل إدارة المهام. يجب أن تبقى أعمال المنصة وتبعياتها وتكاملاتها في خط تطوير واحد متصل.

لا تعني هذه القاعدة دمج التغييرات غير المفحوصة أو تجاوز مراجعات الأمان. الوحدة تعني **مرجع تطوير واحداً**، لا إلغاء المراجعة أو الاختبار أو بوابات القبول.

## 2. ترتيب الفروع والسلطة

1. **فرع التطوير الوحيد:** `codex/mawda-full-platform-implementation`. كل تغيير جديد يبدأ وينتهي عليه.
2. **فرع الإنتاج:** `main`. مستقل ومحمي، ولا يُستخدم للتطوير اليومي أو التجارب أو البناء التطويري.
3. لا يوجد فرع تطوير رسمي ثانٍ أو فرع تكامل مرحلي بديل.

5. الفروع التاريخية والمتخصصة الموجودة حالياً تعامل كمصادر أرشيفية/مراجعة فقط إلى أن تُصالح؛ لا تُعد مراجع تطوير نشطة ولا تُحذف تلقائياً.

## 3. قواعد العمل اليومية

- قبل أي تعديل، اقرأ HEAD الحالي للفرع الموحد وتحقق من نظافة/حداثة نقطة العمل.
- نفّذ التغيير مباشرة على الفرع الموحد، مع commits صغيرة واضحة حسب المجال أو السبب؛ **تقسيم commits مسموح، تقسيم خط التطوير إلى فروع غير مسموح**.
- عند وجود عمل سابق على فرع آخر، لا تنشئ فرعاً جديداً ولا تنقل العمل كله عميانياً. افحص المصدر، وحدد commits والملفات والتغييرات الفريدة، وافحص التداخلات والاعتماديات والاختبارات، ثم انقل فقط التغييرات الصحيحة إلى الفرع الموحد مع حفظ الإسناد والتاريخ حيث أمكن.
- لا تستبدل ملفات كاملة من مصدر قديم إذا كانت النسخة الموحدة تحتوي تغييرات أحدث أو أوسع.
- أي تعارض في السياسات أو الكود أو قواعد البيانات أو صلاحيات الخادم يُوقف الجزء المتأثر حتى يُحسم؛ لا تُخترع حلول أو قيم افتراضية.
- لا يُعلن عن ميزة أنها مكتملة لمجرد وجود كود أو نجاح اختبار منفرد.

## 4. الخطة الإدارية لمصالحة الفروع القائمة

تُدار عملية التنظيف على الفرع الموحد حصراً، بالترتيب التالي:

1. **الجرد:** حصر كل الفروع وطلبات الدمج المفتوحة والمغلقة والـcommits ومصادرها. التمييز بين المتطابق والمتقدم والمتأخر والمتشعب والقديم وغير القابل للتحقق.
2. **تثبيت المرجع:** توثيق SHA الحالي للفرع الموحد، وتأكيد أن كل عمليات النقل ستستهدفه حصراً.
3. **خريطة التداخل:** إعداد مقارنة على مستوى الملفات والمعنى، خصوصاً ملفات Functions المركزية، الصلاحيات، Firestore/Storage rules، المحفظة والمتجر، الوسائط، Flutter، workflows والوثائق.
4. **تصنيف المصادر:** كل تغيير يصنف: مدمج بالفعل، مطابق، فريد صالح للنقل، متعارض، غير آمن، متقادم، أو غير قابل للتحقق.
5. **النقل الانتقائي:** نقل التغييرات الفريدة الصالحة فقط إلى الفرع الموحد، مع مراجعة imports/callers/exports/schema/indexes/rules/tests والاعتماديات.
6. **التحقق:** تشغيل الاختبارات الملائمة على HEAD الموحد بعد النقل، وإصلاح regressions قبل متابعة المجموعة التالية.
7. **الإغلاق الإداري:** بعد التحقق من وصول كل تغيير مطلوب إلى الفرع الموحد أو توثيق سبب استبعاده، تُغلق طلبات الدمج المكررة أو المستبدلة. لا تحذف الفروع التاريخية ولا تعمل force-push أو حذفاً جماعياً؛ أي تنظيف لاحق يحتاج جرداً موثقاً وموافقة منفصلة.
8. **التقرير:** تسجيل الفروع التي تمت مصالحتها، commits المنقولة، الملفات المتأثرة، نتائج الاختبارات، والفجوات المتبقية. لا يُستخدم وصف «اكتمل التوحيد» قبل إغلاق جميع مصادر العمل المطلوبة.

## 5. الخطة التنفيذية للبرمجة والبناء والاختبار

كل دورة تغيير على الفرع الموحد تتبع هذا التسلسل:

1. تحديد المتطلب والقرار المرجعي وحالة تنفيذه.
2. فحص الكود الحالي والاعتماديات ومخاطر التغيير.
3. تنفيذ التغيير على الفرع الموحد فقط.
4. تحديث الاختبارات والوثائق والعقود المتأثرة في نفس خط العمل.
5. تشغيل الاختبارات السريعة المناسبة ثم اختبارات المجال والتكامل والمحاكيات والبناء.
6. فحص نتائج جميع jobs والخطوات، لا الاكتفاء بعلامة نجاح عامة.
7. تسجيل SHA الدقيق وIDs التشغيل وملخص النتائج والقيود.
8. إصلاح كل فشل وإعادة الاختبار على SHA الجديد؛ نجاح SHA سابق لا يثبت قبول SHA أحدث.
9. إجراء مراجعة أمان وصلاحيات وخصوصية واحتفاظ وموثوقية عند تأثرها.
10. إعلان حالة صادقة: منفذ جزئياً، مختبر آلياً، قبول أجهزة/تشغيل حي، أو جاهز للإطلاق. لا تخلط بين هذه الحالات.

تُشغّل workflows البناء والاختبار فقط على فرع التطوير الموحد. لا تُضاف triggers للنشر أو deploy إلى هذا المسار. يمكن أن توجد workflows متعددة بحسب نوع الاختبار، لكن جميعها تعمل على نفس الفرع والـSHA المرجعي؛ تعدد workflows لا يعني تعدد فروع التطوير.

### 11.1 نطاق الفحص الإلزامي

بحسب الملفات والأنظمة المتأثرة، يجب اختيار وتشغيل كل ما ينطبق من الآتي، لا الاكتفاء باختبار واحد:

1. **سلامة المصدر:** formatters، analyzers، linters، type checks، compilation، فحص imports/exports/callers، والتحقق من عدم وجود ملفات أو إعدادات مكررة أو مهجورة.
2. **اختبارات الوظائف:** unit tests، widget/UI tests، contract/schema tests، regression tests، واختبارات الحالات الحدّية والفشل والتزامن وإعادة المحاولة وidempotency.
3. **اختبارات التكامل والبيئة:** integration tests، Firebase Emulator Suite والمحاكيات المناسبة، قواعد Firestore وStorage، Cloud Functions، واجهات API، تدفقات المصادقة والصلاحيات والبيانات والاحتفاظ، بحسب نطاق التغيير.
4. **البناء والتوافق:** بناء كل هدف/منصة متأثرة فعلياً (مثل Web أو Android أو iOS عند توافر toolchain)، وفحص إعدادات release/debug والتبعيات والتوافق. لا يُدّعى اختبار منصة لم تُبنَ فعلياً.
5. **الأمن والخصوصية:** فحص الاعتماديات والثغرات والتراخيص حيث تتاح الأدوات، secret scanning، static security checks، قواعد الوصول، التحقق من المدخلات، حماية البيانات والوسائط، وسجلات التدقيق. يمنع طباعة الأسرار أو تضمينها في artifacts أو logs.
6. **جودة التغيير:** مراجعة diff كاملاً، أثر التغيير على الأنظمة المتصلة، التوافق العكسي، migrations/indexes/rules، الأداء والتكلفة، ومراجعة الوثائق وسجل التتبع والاختبارات المرتبطة.
7. **التحقق من CI:** فحص كل workflow وكل job وكل step ذات صلة، وحفظ روابط التشغيل والـlogs والـartifacts ونتائجها؛ لا تكفي علامة خضراء إجمالية إذا بقي job مطلوب متخطياً أو غير منفذ أو غير مفهوم.
