# الوثيقة الحاكمة الموحدة: سياسة المصدر الوحيد للحقيقة وتوحيد المستودعات وجاهزية الدمج — Mawdda Platform 2026

- الحالة: الوثيقة الحاكمة الموحدة لتوجيهات المالك في نطاق توحيد المستودعات، تنظيم Full Platform، الاختبارات الداخلية، وجاهزية الدمج. موثقة على فرع التطوير؛ لا تجيز الدمج إلى `main` أو النشر أو أي تغيير إنتاجي.
- تاريخ التوثيق: 2026-11-25

## 1. الغاية والنتيجة النهائية

الغاية هي إنهاء التشتت التنظيمي والتقني، وجمع كل كود المنصة وميزاتها وتطبيقاتها وخدماتها واختباراتها ووثائقها وسجلاتها المعتمدة في جسم واحد واضح وقابل لاستمرار التطوير والبناء.

**Full Platform هو جسم المنصة الفعلي ومصدر الحقيقة التنفيذي الوحيد للمنتج.** ليس مستودع تجميع مؤقتاً ولا نسخة مرجعية جانبية. بعد اكتمال النقل والمقارنة والمطابقة والاستيعاب والتنظيم، يجب أن تكون المنصة قابلة للبناء والتطوير مباشرة من هذا الفرع، دون الاعتماد على مستودع تطوير موازٍ أو فرع بديل أو وثائق حاكمة موزعة خارجه.

## 2. الهيكل النهائي المستهدف

يبقى ضمن منظومة Mawdda فقط:

1. المستودع الأساسي `productionhome2022-hash/mawda-platform`، مع الاحتفاظ بفرعه الأساسي القديم `main` بوصفه خط الأساس التاريخي/الرئيسي المحمي.
2. فرع التطوير الوحيد `codex/mawda-full-platform-implementation` داخل المستودع نفسه. هذا هو جسم المنصة الذي يجري عليه التطوير والبناء والاختبارات والتحضير للدمج.
3. مستودع المحاكاة المستقل `productionhome2022-hash/mawdda-5000-simulation-lab`، بوصفه مختبراً منفصلاً فقط، وليس جسماً بديلاً أو مصدراً لكود المنتج.

لا يُسمح ببقاء مستودعات أو فروع تطوير موازية أو مستودعات وثائق منفصلة بعد إتمام الجرد والمقارنة والاستيعاب والتوثيق. لا تُحذف أي مصادر قديمة قبل إغلاق جميع عناصرها وفق هذه السياسة.

## 3. حدود جسم Full Platform

يجب أن يحتوي Full Platform على جميع مكونات المنتج اللازمة للتطوير المستقل، ومنها تطبيقات Flutter والمنصات المدعومة، والخدمات الخلفية وCloud Functions، وإعدادات Firebase وقواعد Firestore/Storage، والواجهات، والاقتصاد والمحفظة والمتجر والاستحقاقات، والمحادثات والغرف والوسائط، والأمن، والاختبارات الاعتيادية، وعمليات GitHub Actions والبناء، ووثائق المنتج والمعمارية والحوكمة والقرارات وسجلات الدمج والاسترداد والفهارس.

يجب نقل الوثائق والسجلات والفهارس المعتمدة إلى داخل شجرة هذا المستودع، مع المحافظة على المصدر والتاريخ وSHA وBatch ID والروابط اللازمة للتدقيق. لا يعني النقل اعتماد محتوى متعارض أو غير موثوق؛ تُسجل حالته ويُحسم قبل اعتماده.

## 4. سياسة الجرد والمقارنة والنقل والدمج

تُنفذ الأعمال بهذا التسلسل الإلزامي:

1. جرد المستودعات والفروع والالتزامات وPull Requests وTags وWorkflows والوثائق والأرشيفات ومصادر الاسترداد.
2. تثبيت SHA مرجعي لفرع Full Platform وتسجيل SHA لكل مصدر.
3. مقارنة الالتزامات ومحتوى الملفات والتغييرات وسلوك الميزات والاختبارات، لا الاكتفاء بتشابه الأسماء.
4. إزالة التكرار باستخدام SHA وBatch ID ومقارنة المحتوى والسلوك.
5. تصنيف كل عنصر: موجود بالكامل، موجود جزئياً، فريد، مكرر، غير مكتمل، متعارض، غير صالح، أو غير محسوم.
6. استيعاب كل عمل فريد ومعتمد أو استكمال الموجود جزئياً داخل Full Platform، بأقل تغيير آمن.
7. توثيق المصدر الأصلي وسبب الاستيعاب والملفات المتأثرة ونتيجة الفحوصات.
8. مراجعة جميع Workflows والاعتماديات والروابط إلى الفروع والمستودعات القديمة، وإزالة الاعتماديات غير المطلوبة.
9. إعادة فحص الشجرة والوثائق والاختبارات وعمليات البناء على الفرع المستهدف.
10. إعداد تقرير إغلاق يثبت مصير كل مصدر قبل أي حذف.

لا يُعد نقل الملفات وحده دليلاً على اكتمال الدمج؛ يجب فحص الوظائف والسلوك والتبعيات والاختبارات. ولا يُحذف عمل فريد أو سجل لازم للتدقيق.

## 5. سياسة الاختبارات — GitHub الداخلي فقط

بموجب توجيه المالك لهذه الخطة، **تقتصر اختبارات التحقق والقبول الخاصة بعملية التوحيد والتنظيم وجاهزية Full Platform للدمج على بيئة GitHub الداخلية**، بما يشمل GitHub Actions وCI والفحوصات الآلية التي تعمل ضمن مستودع GitHub وبيئة تشغيل GitHub المخصصة للـ workflows.

المسموح بحسب الحاجة:
- فحوصات التنسيق والتحليل الساكن.
- اختبارات الوحدة والاختبارات الآلية الموجودة داخل المستودع.
- اختبارات backend وFirebase Emulator إذا شغّلتها Workflows داخل بيئة GitHub المعزولة.
- اختبارات قواعد الأمان والفحوصات الأمنية الآلية داخل GitHub.
- فحوصات الاعتماديات والملفات وYAML وWorkflows.
- عمليات البناء الآلية غير المنشورة التي تعمل ضمن GitHub Actions.
- اختبارات تكامل حتمية داخل بيئة GitHub المعزولة، باستخدام بيانات اصطناعية وخدمات محاكاة محلية/داخلية فقط.

غير مسموح به أو غير مطلوب كشرط لهذه الخطة:
- طلب اختبارات خارجية أو تكليف جهات اختبار خارجية.
- طلب اختبارات فعلية على أجهزة Android أو iOS أو أجهزة أعضاء.
- اختبارات تشغيل حي على Firebase أو GCP أو Cloud Run أو GCS أو خدمات إنتاجية.
- إرسال إشعارات حقيقية أو إجراء مدفوعات أو معاملات مالية حقيقية.
- نشر التطبيق أو الخدمات أو تعديل موارد الإنتاج بغرض الاختبار.
- اعتبار مختبر 5000 شخصية أو أي تشغيل خارج CI شرطاً لقبول عملية التوحيد أو جاهزية الدمج.

يبقى مستودع مختبر 5000 شخصية مستقلاً ضمن الهيكل المسموح، ولا يُنقل كود المنتج إليه ولا يصبح مصدراً بديلاً للمنصة. لا يشكل تشغيله شرطاً لهذه الخطة أو لبوابة الدمج المحددة هنا، ولا يجوز تشغيله أو تغيير حدوده إلا وفق قرار مالك مستقل وصريح.

**حدود الدلالة:** نجاح اختبارات GitHub الداخلية يثبت فقط أن الفحوصات المحددة نجحت على SHA المحدد وفي البيئة التي شُغلت فيها. لا يجوز وصف ذلك بأنه اختبار أجهزة فعلية أو اختبار خدمات حية أو قبول إطلاق إنتاجي. ولا تطلب هذه السياسة تلك الاختبارات؛ تبقى قرارات الإطلاق والإنتاج منفصلة وخاضعة لموافقة المالك.

## 6. معيار جاهزية Full Platform للدمج مع main

الهدف من عمليات التوحيد والتنظيم هو أن يصبح Full Platform، بعد اكتمال العمل المستقبلي المطلوب، مرشحاً منظماً وجاهزاً لفتح Pull Request والدمج مع `main` دون الحاجة إلى إعادة هيكلة تنظيمية جوهرية.

لا يُعلن تحقق الجاهزية إلا عند وجود أدلة GitHub داخلية على ما يلي:

- اكتمال جرد المصادر ومصير كل عنصر.
- استيعاب الأعمال الفريدة المعتمدة وعدم وجود أعمال معروفة مجهولة المصير.
- عدم وجود جسم تطوير موازٍ أو اعتماد غير مبرر على Recovery أو مستودع قديم.
- اتساق بنية المشروع والاعتماديات والإعدادات والواجهات والعقود المشتركة.
- وجود الوثائق والقرارات والسجلات والفهارس اللازمة داخل المستودع.
- مراجعة Workflows والـ CI والتأكد من أنها لا تنشر ولا تعدل الإنتاج ولا تستدعي محاكاة 5000 شخصية.
- نجاح الفحوصات والاختبارات والبناء الداخلي المحدد على SHA المرشح.
- معالجة تعارضات الدمج المعروفة ومراجعة الفرق مع `main` دون دفع الدمج.
- وجود تقرير جاهزية يحدد SHA، والفحوصات المنفذة ونتائجها، والاستثناءات المعروفة.

تعني عبارة «جاهز للدمج» جاهزية تقنية وتنظيمية لطلب الدمج والمراجعة. لا تعني تنفيذ الدمج تلقائياً، ولا تتجاوز موافقة المالك الصريحة والمستقلة على الدمج إلى `main`.

## 7. قواعد الحذف والتنظيف

الحذف هو آخر مرحلة، وليس وسيلة للجرد. لا يُحذف أي فرع أو مستودع أو أرشيف قبل:
- توثيق آخر SHA ومحتوياته المهمة.
- مقارنة جميع الالتزامات والملفات والتعديلات الفريدة.
- نقل ما يجب الاحتفاظ به والتحقق من وجوده داخل Full Platform.
- توثيق العناصر المكررة أو المستبعدة وسبب ذلك.
- فحص Pull Requests وWorkflows والروابط والاعتماديات.
- إثبات عدم وجود عمل مطلوب غير مستوعب.

يُحتفظ بـ `main` وFull Platform ومختبر 5000 شخصية. ولا يُحذف أو يُعاد إنشاء أو يُنقل أي مورد إنتاجي أو إعداد Firebase أو هوية تطبيق iOS أو سر أو بيانات إنتاجية ضمن هذه الخطة.

## 8. قواعد التطوير المستقبلي ومنع عودة الفوضى

- جميع تطويرات المنتج المستقبلية تنفذ على Full Platform وحده.
- لا تنشأ فروع تطوير بديلة أو أجسام منصة موازية.
- لا تنشأ مستودعات منفصلة لميزات المنتج أو وثائقه.
- أي فرع مؤقت تفرضه آلية GitHub يجب أن يكون قصير العمر، مرتبطاً بتغيير محدد، ويعاد إلى Full Platform ثم يغلق؛ لا يتحول إلى خط تطوير دائم.
- كل تغيير يرفق بسبب واضح واختبارات GitHub داخلية وتوثيق مناسب.
- تحفظ القرارات المعتمدة والمعلقة منفصلة، ولا يتحول الاقتراح إلى قرار دون موافقة المالك.
- لا دمج إلى `main` ولا نشر ولا تعديل إنتاجي ولا تفعيل فوترة أو خدمات مدفوعة دون موافقة مستقلة صريحة من المالك.

## 10. حسم التعارض مع الوثائق الأقدم

هذه السياسة توثق توجيه المالك الأحدث بتاريخ 2026-11-25 بشأن نطاق اختبارات خطة التوحيد وجاهزية الدمج. وهي تعدل أي نص أقدم يجعل تشغيل مختبر 5000 شخصية أو اختبار أجهزة فعلية أو اختبار خدمات حية شرطاً مسبقاً لإغلاق عملية التوحيد أو قبول جاهزية الدمج.

تبقى حدود الأمان ومنع النشر والإنتاج وحماية البيانات والموارد الحية سارية. كما تبقى متطلبات القبول النهائي للإطلاق منفصلة عن جاهزية الدمج، ولا تعتبر هذه السياسة تصريحاً بالإطلاق أو تنازلاً عن موافقات المالك السيادية.

## 11. سجل الحالة

- السياسة والخطة موثقتان في هذا الملف على فرع Full Platform.
- توثيق السياسة لا يعني أن الجرد أو النقل أو الاختبارات أو الحذف قد نُفذت.
- حالة كل مرحلة تُحدّث فقط بعد تنفيذها وإرفاق دليلها.
- أي تعديل لهذه السياسة يتطلب توجيهاً صريحاً من المالك وتحديث سجل القرارات والتتبع.

## 12. التوجيهات والتوضيحات الملزمة الموحّدة من المالك

هذا القسم يجمع التوضيحات التنفيذية اللاحقة مع السياسة والخطة أعلاه في مرجع واحد. لا يجوز التعامل معها كقرارات منفصلة أو متعارضة أو الاكتفاء بقراءة ملخص قديم.

### 12.1 Full Platform هو المنصة نفسها

- فرع `codex/mawda-full-platform-implementation` ليس مجرد فرع تجميع أو مكان مؤقت لحفظ الملفات؛ إنه جسم المنتج الفعلي الذي ستُبنى عليه المنصة وتطبيقاتها وتستمر عليه أعمال التطوير.
- يجب أن يحتوي هذا الفرع على كامل شجرة المنتج اللازمة للبناء والتطوير المباشر: التطبيقات، الواجهات، الخدمات، الحزم، الإعدادات، الاختبارات الداخلية، عمليات البناء، الوثائق والسجلات والفهارس المعتمدة.
- لا يجوز أن تعتمد عملية بناء المنتج أو تطويره بصورة دائمة على كود أو وثائق تشغيلية موزعة في Recovery أو مستودع آخر أو فرع تطوير موازٍ.
- يجب أن تكون بنية Full Platform نظيفة ومتماسكة ومفهومة، بلا ملفات يتيمة أو نسخ مكررة أو مسارات متضاربة أو إعدادات بناء مكسورة أو اعتماديات غير مبررة. لا تُنشأ مجلدات أو طبقات شكلية لمجرد تحسين المظهر؛ التنظيم يتبع البنية الفعلية للتطبيق.
- المقصود بعبارة «المنصة تعمل مباشرة على Full Platform» أن مصدر الشيفرة والبناء والتطوير المستمر هو هذا الفرع. لا تعني هذه العبارة نشر المنصة أو تشغيل موارد الإنتاج أو منح تصريح بتغييرها.

### 12.2 نطاق الاختبارات المسموح والمطلوب

- جميع اختبارات هذه الخطة، بما فيها التحقق من النقل والتكامل والتنظيم وجاهزية الدمج، تُنفذ حصراً ضمن بيئة GitHub الداخلية: GitHub Actions وCI والفحوصات والاختبارات والبناء الآلي داخل بيئة الـ workflow.
- لا نطلب من المالك أو من طرف خارجي إجراء اختبارات خارج GitHub، ولا اختبارات فعلية على أجهزة أو حسابات أعضاء، ولا اختبارات تشغيل حي على خدمات Firebase أو GCP أو الإنتاج.
- لا يُشترط تشغيل مختبر 5000 شخصية لإغلاق مراحل التوحيد أو إعلان جاهزية فرع Full Platform لطلب الدمج. يظل المختبر مستودعاً مستقلاً مسموحاً به وفق حدوده، ولا يتحول إلى جسم منتج أو شرط اختبار خارجي لهذه الخطة.
- يجب أن تكون بيانات الاختبار اصطناعية، والخدمات المستخدمة محلية أو محاكاة أو معزولة داخل بيئة GitHub. يمنع إرسال إشعارات حقيقية أو تنفيذ مدفوعات أو إجراء عمليات تمس أعضاء أو بيانات حقيقية.
- إذا تعذر تشغيل اختبار داخل GitHub، يسجل الاختبار بوصفه غير منفذ مع السبب والأثر؛ لا يستبدل باختبار خارجي، ولا يدعى نجاحه.
- نجاح GitHub CI دليل على الاختبارات التي شغلتها Workflows فعلياً على SHA محدد فقط. لا يُوصف بأنه قبول أجهزة أو اختبار حي أو إثبات جاهزية إطلاق إنتاجي.

### 12.3 شرط الجاهزية المستقبلية للدمج مع main
