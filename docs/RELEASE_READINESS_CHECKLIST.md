# Mawadda Release Readiness Checklist

This checklist is a release gate, not a statement that the listed work is complete. Keep the product on the development branch until every applicable gate is evidenced and reviewed.

## 1. Repository and continuous integration

- [x] Validate the development branch with Flutter analysis, Flutter tests, and a Flutter Web release build.
- [x] Validate Cloud Functions TypeScript compilation and backend unit tests.
- [x] Validate Firestore and Storage rules with Firebase Emulator Suite tests.
- [ ] Add and commit `pubspec.lock` generated by the approved Flutter SDK.
- [ ] Add and commit `functions/package-lock.json` generated from the reviewed `functions/package.json`.
- [ ] Change CI dependency installation to lockfile-enforcing commands (`flutter pub get --enforce-lockfile` and `npm ci`) after the lockfiles are committed.
- [x] Pin Flutter to 3.47.9 and Node to 20 in validation/deployment workflows.
- [x] Restrict manual production deployment dispatch to the repository owner and require explicit approval; deployment repeats Flutter, backend, and Firestore/Storage emulator validation before Hosting deploy.
- [x] Block Hosting deployment while the CLI target, FlutterFire project ID, or generated Firebase app identifiers are mismatched/placeholders.
- [ ] Commit dependency lockfiles and move installation to lockfile-enforcing commands.
- [ ] Re-run all checks against the final release candidate commit.

## 2. Firebase project configuration

- [ ] Independently confirm the production Firebase project is `mawda-app-2026`.
- [ ] Register and verify the required Firebase apps for each supported platform.
- [ ] Regenerate `lib/firebase_options.dart` using FlutterFire CLI for the confirmed project; do not hand-invent app IDs or API keys.
- [ ] Verify every generated platform option points to the intended Firebase project and registered app.
- [ ] Verify Firebase Authentication providers, authorized domains, Firestore, Storage, and Cloud Functions are configured.
- [ ] Keep service-account keys, private keys, tokens, and local credential files out of Git.
- [ ] Verify Hosting configuration and deployment target before any production deployment.

## 3. Owner access and operational security
- [ ] Verify suspended/banned/unknown account states are denied for both sides of new coin transfers.
- [ ] Verify suspended/banned/disabled/unknown account states are denied on direct-message send, room join, and room-message send, including already-joined members.

- [ ] Verify the intended owner account through Firebase Authentication using a trusted operator workflow.
- [ ] Review and authorize the owner bootstrap script before running it against the real project.
- [ ] Provision the `platformOwner` claim only after independent identity verification.
- [ ] Configure and test the actual MFA enrollment, challenge, session freshness, recovery, and revocation flow.
- [ ] Confirm privileged operations are server-enforced and produce audit records.
- [ ] Confirm no plaintext password access, client-controlled admin flags, or unlogged covert surveillance exists.
- [ ] Keep registration closed until the owner has reviewed and explicitly configured the registration policy.

## 4. Member experience and product workflows

- [ ] Test registration, email verification, sign-in, sign-out, password reset, and account recovery against a non-production Firebase environment.
- [ ] Test profile completion, editing, validation, privacy, and unique username behavior on physical devices.
- [ ] Test the 500-coin verified-email reward for exactly-once behavior.
- [ ] Test coin transfer quoting, fee calculation, stale quote rejection, atomic ledger writes, idempotency, and both parties' wallet histories.
- [ ] Complete and test direct-message UI, pagination, delivery/read state, push notifications, block/report, and media workflows.
- [ ] Complete and test room discovery, invitations, moderation, rental billing, voice/video, and room finance.
- [ ] Complete and test store catalog, secure purchase verification, premium entitlements, coin packs, and reward anti-abuse controls.
- [ ] Complete the owner console modules for platform settings, identity/content, backgrounds, stores, finance, trust/safety, analytics, backups, and incident response.

## 5. Media, privacy, and safety

- [ ] Implement authenticated media upload/download paths with MIME, size, ownership, and content validation.
- [ ] Implement and test server-side retention and deletion policies; clearly disclose that downloaded copies cannot be remotely guaranteed to disappear.
- [ ] Bundle the approved launch background locally as the stable fallback for remote background load failures.
- [ ] Test background previews, responsive crops, contrast, reduced motion, rollback, and fallback behavior.
- [ ] Complete age assurance, minor-safety, moderation, reporting, blocking, appeals, and privacy workflows.
- [ ] Complete applicable legal and policy review for each launch market.

## 6. Cross-platform release verification

- [ ] Android phones and tablets: install, sign-in, core workflows, portrait and landscape.
- [ ] iPhone and iPad: build, install, sign-in, core workflows, portrait and landscape.
- [ ] Windows, macOS, and Linux: build and smoke-test supported desktop workflows.

- [ ] Test touch, mouse, keyboard navigation, accessibility, screen readers, and reduced-motion settings.

## 7. Release authorization

- [ ] All blocking checks are green on the exact release candidate commit.
- [ ] Security review and operational review are complete and recorded.
- [ ] Production Firebase configuration and deployment target have been independently verified.
- [ ] Owner explicitly approves merging to `main`.
- [ ] Owner separately approves production deployment.
- [ ] Verify post-deployment health, authentication, Firestore access, Cloud Functions, and rollback readiness.

### Additional MAWADDA AI identity and link-policy release gates

- [ ] Every AI character displays a persistent, accessible AI badge on avatar/cover and profile header; activating it explains the AI identity; it is not styled as human verification.
- [ ] AI activity, followers, reactions, and popularity are separately labeled and never counted as human-member activity.
- [ ] Members without successful biometric verification cannot post links in any chat or room. Biometrically verified members receive the free YouTube, Facebook, Instagram, and X/Twitter entitlement across DMs and public/rented-private room chats.
- [ ] Authenticated room owners and authorized moderators can post only verified YouTube, Instagram/Reels, and Facebook URLs in public/private rented rooms; authorization is server-side and moderator revocation takes effect immediately.
- [ ] One-to-one private messages allow YouTube, Facebook, Instagram, and X/Twitter URLs only for members whose biometric status is server-confirmed as verified; the platform Super Admin exception remains separately gated.
- [ ] URL tests cover redirects, shorteners, lookalikes, IDN/punycode, deceptive subdomains, credentials, unsafe schemes, obfuscation, embedded URLs, rich previews, and authorization bypass.
- [ ] Global/module/character shutdown stops active generation promptly and revokes AI tool permissions.


### Super Admin link exception and AI badge presentation

- [ ] Platform Super Admin, verified server-side by platformOwner claim and fresh MFA/step-up session, can send ordinary HTTP/HTTPS links to any domain in direct chats, public rooms, and rented private rooms.
- [ ] Dangerous executable schemes, malformed links, and credential-bearing URLs remain blocked; safe-preview and phishing/malware controls are tested.
- [ ] Unverified ordinary members remain blocked from all links. Biometrically verified members receive free YouTube, Facebook, Instagram, and X/Twitter links across DMs and public/rented-private room chats; room owners/moderators retain their room-scoped YouTube, Instagram/Reels, and Facebook allowlist.
- [ ] AI badge appears as a small visual AI marker on avatar or cover only; no explanatory pop-up and no AI announcements inside direct chats or rooms.


### Free biometric-verification link entitlement release gates

- [ ] A trusted biometric verification workflow is implemented and independently tested; a client cannot set or forge status, expiry, or revocation fields; eligibility requires a future server-owned `expiresAt` and no `revokedAt`.
- [ ] The entitlement is free and available in direct messages, public-room chats, and rented-private-room chats only while the server-owned biometric verification remains valid.
- [ ] Expired, revoked, failed, or pending biometric status immediately loses the link entitlement; tests cover stale state, cross-account attempts, and status changes.
- [ ] Approved destinations include YouTube, Facebook, Instagram, and X/Twitter official domains (including youtu.be and youtube-nocookie.com). Shorteners such as `t.co` remain blocked until safe redirect verification is implemented.


## Additional approved profile and financial-control release gates

### Biometrically verified member profile links
- [ ] Active verified members can save optional Instagram, X/Twitter, Facebook, and WhatsApp profile links; each is individually editable, removable, and hideable.
- [ ] Visitors see only links the member explicitly published and only when profile visibility permits.
- [ ] Only normalized HTTPS URLs on the provider's approved official domains are accepted; malformed/deceptive URLs, credentials, unsafe schemes, and shorteners are rejected.
- [ ] Expired/revoked biometric verification immediately hides published links and blocks publishing/editing; clients cannot forge verification state or bypass profile read authorization.
- [ ] Cross-account, privacy, expiry, revocation, and URL-validation tests pass.

### Super Admin financial freeze and coin adjustments
- [ ] Owner-only global and per-operation switches pause/resume top-ups/purchases, coin crediting, transfers, refunds/redemptions/withdrawals where supported, rewards, and administrative adjustments.
- [ ] Member-level restrictions independently control sending, receiving, top-ups, and refunds/redemptions; enforcement is server-side across all callable/transaction paths and open sessions.
- [ ] In-flight transfers and payment-provider callbacks are safely frozen/reconciled; no duplicate credit or silent loss occurs when resuming.
- [ ] Suspected fraud triggers reversible hold/freeze and investigation by default; partial/full forfeiture requires a substantiated case and recorded reason.
- [ ] Every freeze, deduction, or zero-balance action requires fresh MFA, explicit target/action/amount, impact preview, separate confirmation, idempotency, and immutable audit.
- [ ] Coin forfeiture is an atomic double-entry ledger transaction to the platform treasury/forfeiture account; historical entries are never edited/deleted, balances never go negative, and real-money refunds remain separate provider workflows.
- [ ] Member notice, appeal/review, compensating reversal, bulk-action alerts, unauthorized-access tests, and audit completeness are verified.
